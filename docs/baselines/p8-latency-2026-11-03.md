# P8 impact/tests latency at 1M edges (2026-11-03)

R13 L3 found a Critical 1M-edge hub latency failure at `0b51585`:
`impact --depth 3` 1,132.5 ms and `tests` 1,335.6 ms. This note pins the
corpus, the budget, and the post-fix measurements.

## Corpus

| property | value |
|---|---|
| path | `/tmp/kg-r13-l3/edges1m-sub` |
| files | 1,203 |
| symbols | 205,206 |
| edges | 1,368,522 |
| hub | `synth/core.py`; 204,002 distinct direct callers |

The corpus is synthetic and adversarial: one hub symbol is called by nearly
every function, so a reverse BFS from the hub reaches almost the whole graph.
It is a stress shape, not a claim about a typical 1M-edge repository.

## Method

- Release binary, `--no-journal`, explicit `--root`.
- `bash tests/scripts/timing_assert.sh 7 <label> <budget> <command...>`.
- Budgets from the P8 amendment §7.5: `impact --depth 3` < 150 ms,
  `tests --depth 10` < 200 ms at 1M edges.
- Host load was not controlled; best-of-7 reduces transient noise.

## Results

| command | best-of-7 | budget | result |
|---|---:|---:|---|
| `kg impact synth/core.py --depth 3` | **97.1-144.3 ms** | 150 ms | PASS |
| `kg impact synth/core.py --depth 3 --edges all` | **104.1-146.9 ms** | 150 ms | PASS |
| `kg tests synth/file0000.py --depth 10` (100 tests) | **9.5 ms** | 200 ms | PASS |
| `kg tests synth/file0000.py --depth 10` (10,000 tests) | **95.2-113.2 ms** | 200 ms | PASS |
| `kg tests synth/core.py --depth 10` (10,000 tests) | **63.0 ms** | 200 ms | PASS |

The zero-test corpus exercises the no-test fast path. A test-rich 1.37M-edge
corpus with 100 tests measures 8-10 ms, and a 10,000-test copy measures
63-113 ms; both use the forward-from-tests path. Reverse BFS remains for
indexes with more than 20,000 test-shaped symbols and is not measured here.

The impact universe uses exact per-kind source-file meta counters, so
module-level callers are included and the `--edges all` shape stops at depth
1.

Stress and representative controls:

| corpus | command | best-of-5 | budget |
|---|---|---:|---:|
| 3.1M-edge hub (`edges1m`) | `impact --depth 3` | 254.3 ms | over 1M budget (stress only) |
| 3.1M-edge hub (`edges1m`) | `tests --depth 10` | 363.4 ms | over 1M budget (stress only) |
| 987k-symbol representative (`/tmp/kg-r11-a3/synth1m`) | `impact --depth 3` | 5.1 ms | PASS |
| 987k-symbol representative (`/tmp/kg-r11-a3/synth1m`) | `tests --depth 10` | 5.6 ms | PASS |

## Changes that produced the pass

1. Removed the full inbound `ORDER BY` from both BFS queries; output ordering
   is selected by a bounded heap after the BFS.
2. Added `edges_dst_cover(dst_id, kind, src_id, site_line)` so BFS reads
   `src_id`/`site_line` without table lookups.
3. Direct impact level groups by `ss.file_path` in SQL when `--context` and
   `--explain` are absent, so the hub's 204k edges produce 1,202 records.
4. BFS stops when all reachable files (impact) or all callable symbols
   (`tests`) are covered.
5. The impact universe is read from exact per-kind source-file meta counters
   (`edge_*_src_files`), with an edge-scan fallback for old indexes. This
   includes module-level callers; the earlier callable-only bound silently
   under-reported them.
6. `tests` returns no-results immediately when the index has no test-shaped
   symbols. With up to 20,000 test symbols it searches forward from each test;
   larger sets use the reverse BFS with callable coverage and test coverage
   early stops.

## Caveats

- The 3.1M-edge corpus is outside the 1M budget and remains a stress case.
- The corpus and index are local-only; CI does not run this gate.
- An existing index built before `edges_dst_cover` still passes the 1M gate
  because the `ORDER BY` removal is the dominant fix; a rebuild adds the
  covering index.
