## Verdict

The R14 evidence is trustworthy for a set of narrow factual claims: the
committed GT recall numbers reproduce at `e74deab`; the raw utility arithmetic
reproduces; the named fix code and tests exist; the budgeted 1.37M-edge latency
shapes pass at `e74deab`; and the 100-test forward path is fast. It is not a
REMOVE-grade evidence base.

reports as they exist:

  `5706dff`; L3 and L4 are at `d714f29`; L5 is at `e74deab`.

### C5. The correctness evidence is not target-correct or immutable enough for REMOVE

The GT gates are recall-oriented or shape-oriented, not target-correct:

- Tests: `tests_recall.py:57-85` matches `file:line` only. The precision half
  counts emitted rows whose leaf name matches `test_*`/`test[A-Z]`; it does not
  check reachability, path policy, or the pinned qualname. A wrong test symbol
  at the right line passes. The 2,679 emitted rows are 782 unique `file:line`
  values across the 20 target queries (0 within-query duplicates). The number
  is a per-query shape check, not 2,679 distinct correct pointers.
- Imports: `import_recall.py:90-126` accepts any import-shaped line whose
  source text contains the target leaf. A wrong module with the same leaf
  passes. It is a source-evidence proxy, not exact target verification.
- Inheritance: `inheritance_recall.py:62-66` does substring matching on the
  child qualname and has no precision half and no negative control. A feature
  that over-reports children would still get 17/17.
- The dead probe oracle is not checked in. It reproduces 6/50 only when the
  file set is the 252 indexed vihap files. The method says "every `.py` file"
  (`dead-precision-2026-11-03.md:11-13`); a literal reading includes 9,269
  `.py` files (including `.venv/` and `build/lib/` copies) and gives 0/50
  zero-reference candidates. The doc says "local probe, not a checked-in gate"
  (`:60`), so a future auditor cannot reproduce the exact set without
  re-deriving the file scope.
- The `impact` regression test is ineffective. `tests/cli.rs:1177` uses
  `m1.py` with one function and no self-edge; `records.len()` is 1, below the
  old callable-file universe of 2, so the pre-fix `5706dff` binary also returns
  `top.py`. L4 I10 reproduces this. `remediation.md:78` cites this test as the
  regression for the impact universe fix; it does not guard the fix.
- GT runs have no checked-in raw logs; the docs say the gates are local-only.
  The corpus revisions are recorded (`vihap d060ace`, `finguard dddfe07`), but
  the exact commands and outputs are not part of the baseline commit.

Consequence: the GT passes support "the tool emits the pinned rows" but not
"the feature is correct in general." For REMOVE, correctness must be at least
as strong as the value claim; this battery does not reach that bar.

## Suggestions

1. Freeze the review set in a commit before wave 1: `README.md`, `lenses/`,
   `remediation.md`, `protocol.md`, prompts, expected oracles, and the scoring
   script. Record SHA-256 for each. No report may be rewritten after the first
   vote without a dated correction that invalidates the affected cells.
2. State one estimand before the run: per-cell n>=5 or a pooled model with
   host as a pre-registered blocking factor. Do not choose after seeing the
   deltas.
3. Generate the utility table from `metrics-p8.jsonl`; do not transcribe. Fix
   the agy 18.0/18.0 values in the table body, not in an appended note.
4. Add a `--root` preflight or a cwd fallback for non-git corpora so every
   treatment cell does not pay a failed first command. Record root mode as a
   covariate.
5. Audit OpenCode per cell: record cwd, files read, and whether the answer
   used the assigned corpus. Report the exclusion direction, not just the
   count.
6. Enforce the full control-tool whitelist, not only the pinned feature.
7. Use multiset scoring for duplicate rows, or change the protocol to say
   duplicates are ignored. Do not leave the scorer and protocol disagreeing.
8. Add negative controls to imports, tests, and inheritance GT; assert exact
   qualnames and target modules, not substrings/leaves.
9. Check in the dead probe oracle and define "corpus files" explicitly. A
   result that changes from 6/50 to 0/50 when `.venv/` and `build/lib/` copies
   are included is not a stable gate.
10. Add a regression test that fails on the pre-fix binary. The current
    `impact_depth_two_includes_module_level_caller` does not.
11. Add a test-bearing latency corpus to the gate; name the target file, test
    count, and index hash. Keep the 0-test, <=1000-test, and >1000-test shapes
    as separate rows.
12. Add `--edges calls,imports` and `calls,inherits` budget rows; add an
    old-index fallback warning or a forced rebuild.
13. Make the docs one source of truth for latency and parity. Delete or update
    the stale `EVALUATION.md:300-301` rows and `src/mcp.rs:3-4`.
14. Record raw GT and timing output in the evidence directory; local-only gates
    need at least a checked-in command log and corpus revision.

## Checklist for a future REMOVE-grade battery

A REMOVE decision should not be considered until every item below is true.

| Area | Required evidence |
|---|---|
| Freeze | Decision rule, prompts, oracles, scoring code, and corpora committed before the first cell; SHA-256 and commit recorded; no post-freeze edits without invalidating affected cells |
| Rule | One pre-registered estimand; minimum effect; n>=5 per cell or a pre-registered pooled model; >=2 task shapes per feature; confidence intervals; explicit exclusion rule; no KEEP when any Critical is open |
| Independence | Per-lens read log or hash; forbidden-file list; no prior verdicts; disclosed leaks; all reports written against the same baseline |
| Utility | >=5 runs per cell; >=2 shapes per feature; git-rooted or `--root`-preflighted corpora; zero failed mandatory commands; full control whitelist; per-cell cwd/root audit; multiset scoring; table generated from raw metrics |
| Correctness | Pinned corpus revisions; checked-in construction scripts and raw logs; exact target/qualname/module assertions; negative controls; precision not shape-only or duplicate-inflated; dead oracle checked in with a defined file set |
| Latency | Checked-in corpus generator and hash; test-free, <=1000-test, >1000-test, mixed-edge, and old-index cases; named target/seed/test count; warm and cold cache; median/p95; host load; build RSS and index size |
| Contract | Regression tests that fail on the pre-fix binary; MCP/CLI parity for success and error; docs and code consistent; no open Critical |
| Removal | Packet with CLI/MCP/journal/payload/tests/GT/docs/skills surfaces, schema residue, consumer migration, rollback, residual risk, and owner sign-off |
| Vote | >=4/5 value lenses vote REMOVE at the same baseline; L6 is TRUSTWORTHY for the evidence used; any lens that cannot separate "no value" from "shape did not show value" votes DEFER/IMPROVE |
| Record | All review artifacts committed at the baseline; no untracked or mid-audit files; raw logs and index hashes included |

## Blinding and independence statement

The prompts (`lenses/L1-correctness.md` ... `L5-removal.md`) contain the
forbidden list: R13 `reports/`, `decision-matrix.md`,
`R13-P8-keep-improve-remove.md`, the utility report's interpretation/verdict,
and another reviewer's report. L6 may read prior reviews but must not vote.

What can be verified from the artifacts:

- L1 states it derived expected sets before opening the committed GT JSON
  (`L1.md:6-12`).
- L2 states it did not read the utility report's Interpretation/Threats/
  Verdict, but did read the Validity/Results table (`L2.md:12-16`); that is
  allowed by the letter of the R14 evidence list, but it is an anchoring risk.
- L4 discloses a real leak: one grep returned `docs/evaluation.md` §11 verdict
  labels (`L4.md:19-23`); it says no decision uses them.
- L5 discloses the same class of leak (`L5.md:24-30`).
- L3 and L4 state they did not read another R14 report. L3's report was
  rewritten during this audit, so its independence from later reports cannot
  be established from the file alone.

What cannot be verified: whether any lens opened a forbidden file, whether L3's
rewrite used L4 or L5, and which version of `README.md`/`remediation.md` each
lens read. There are no access logs and no committed hashes. The disclosed L4/
L5 leaks are limited and do not appear to drive their decisions, but they are
real blinding deviations.

The larger independence problem is not deliberate contamination. It is that
the reports were written against different commits, L5 arrived after the
others, and the rule file was modified after the first reports. That makes a
simultaneous five-lens vote impossible to reconstruct.
