## 1. Method

Every timed command uses the P8 harness:

```
bash tests/scripts/timing_assert.sh <runs> <label> <budget-ms> <binary> <command...>
```

It sends stdout/stderr to `/dev/null`, accepts exits 0/1/2, and reports the
minimum of N runs. Best-of-N (min) is biased upward by host load, never
downward. Both budget corpora were rebuilt with the `d714f29` binary so the
new meta counters exist; row counts are unchanged.

## 7. The `tests` path at d714f29

`test_impact` at `d714f29` has exactly two behaviors:

1. **Guard**: `has_test_candidates` false → immediate no-results (0.004 ms).
2. **Reverse BFS**: the original per-level traversal, with `SELECT DISTINCT`,
   reached whenever the index contains at least one test-shaped symbol. There
   is no forward search, no `total_test_symbols`, and no early stop on found
   tests at this baseline.

Reverse-branch cost is structural. Per-level simulation on the 1.37M corpus,
seed `synth/file0000.py`:

```
depth 1: frontier_in=171   chunks=1  rows=371   new=202   visited_callables=372/204003     1.3ms
depth 2: frontier_in=202   chunks=1  rows=433   new=433   visited_callables=805/204003    32.1ms
depth 3: frontier_in=433   chunks=1  rows=926   new=922   visited_callables=1727/204003   26.6ms
depth 4: frontier_in=922   chunks=2  rows=2013  new=2003  visited_callables=3730/204003   51.6ms
depth 5: frontier_in=2003  chunks=5  rows=4337  new=4268  visited_callables=7998/204003   75.9ms
depth 6: frontier_in=4268  chunks=9  rows=9298  new=8925  visited_callables=16923/204003  82.1ms
depth 7: frontier_in=8925  chunks=18 rows=19475 new=17648 visited_callables=34571/204003  78.4ms
depth 8: frontier_in=17648 chunks=36 rows=38632 new=31068 visited_callables=65639/204003 156.3ms
```

## 8. New scans and fallback paths

`git show d714f29 -- src/query.rs src/build.rs` adds `has_test_candidates`, the
meta-backed `impact_source_files`/`total_callables`, and the build counters.

Index-backed and O(1) as intended:

```
SELECT value FROM meta WHERE key='edge_all_src_files'     # 0.004 ms
SELECT 1 FROM symbols WHERE ... name GLOB 'test_*' LIMIT 1
`--MULTI-INDEX OR  |--SEARCH symbols USING INDEX symbols_name (name>? AND name<?) ...
```

Residual costs:

- `impact_source_files` **fallback** is `COUNT(DISTINCT ss.file_path) FROM
  edges e JOIN symbols ss ...`. It runs for (a) indexes built before
  `d714f29`, and (b) **mixed kind subsets** such as `--edges calls,imports`
  and `--edges calls,inherits`, which have no meta key. Cost 73.1 ms at 1.37M
  edges, 168.2 ms at 3.1M.
- `test_impact` still materializes a `DISTINCT` temp b-tree per frontier chunk
  (81.3-94.2 ms pure-SQL on the hub frontier). Later commits remove it; this
  baseline does not.
- `has_test_candidates` is index-backed but its `LIMIT 1` makes it O(1) only
  for indexes with no tests; with tests present it returns true and the BFS
  cost follows.

All BFS edge reads use the covering index:

```
SEARCH e USING COVERING INDEX edges_dst_cover (dst_id=? AND kind=?)
```

| test-shaped symbols | leaf d10 | hub d10 | path |
|---:|---:|---:|---|
| 0 | **6.9-7.3 ms** | 8.6 ms | guard |
| 1 | **621.3 ms** | 172.6 ms | reverse BFS |

The count is irrelevant at this baseline: a single test symbol defeats the

short-circuits after one level; a leaf target does not.

Why this is Critical: the §7.5 row is `tests --depth 10 < 200 ms at 1M edges`,
naming neither a target file nor a test count. Real repositories carry test
symbols, so the common shape is 613.7-621.3 ms, 3.1x over. The gate corpus has
zero tests, so the row appears green. The only synthetic element is the
inserted test rows on a copy of the gate corpus; the traversal itself is the
unmodified `d714f29` code path that measured 623.4 ms at load 3.8 on `5706dff`.

If the owner rules that the row is scoped to test-free synthetic corpora,
reclassify C3 as Important — but it must not be silently closed. Note that
later commits after this baseline (`5858a11`, `1d22c57`, `e74deab`) address
this with DISTINCT removal, an early stop, and a forward search for small test
sets; those are outside the baseline assigned to this report.

### Important

**I1 — Mixed `--edges` subsets still pay the fallback scan and exceed the
150 ms row: `calls,imports` 200.6 ms, `calls,inherits` 176.6 ms** (load 7.2).

```
FAIL: impact-mixed-calls-imports 200.6ms > 150ms
FAIL: impact-mixed-calls-inherits 176.6ms > 150ms
```

The meta keys cover three single kinds and the all-three union only. A
two-kind subset has no key, so `impact_source_files` runs the 73.1 ms edge
scan and the depth-1 pass follows. Cheapest remaining instance of the C2
class: two more counters, or normalize the key to the actual subset.

**I2 — Indexes built before `d714f29` pay a *worse* fallback than at
`5706dff`.** On the then-unrebuilt 3.1M index:

```
timing: impact-3.1M-oldindex-d3 best-of-5 393.2ms     # was 269.4 ms at 5706dff
timing: tests-3.1M-oldindex-d10 best-of-5 13.8ms      # guard needs no meta
```

The fallback is now an edge scan (168.2 ms at 3.1M) instead of the old symbol
scan (28.6 ms). Nothing forces a rebuild or warns that the counters are
missing. At small scale the fallback is cheap (old self index: `impact`
5.9 ms, `tests` 5.4 ms), so the risk is concentrated at scale.

**I3 — `impact` depth-1 still makes two full passes over the target's inbound
edges.** `direct_impact_records` (96.2 ms) plus a separate
`COUNT(DISTINCT sf.path)` (24.9 ms) whose value equals the grouped row count
(1,202), both at the same low-load in-process measurement. The redundant pass
is about 21% of the depth-1 cost (24.9 / 121.1). Depth 1 is therefore slower
than depth 2 or 3, which use the meta counter.

**I4 — `dead` is 789.7 ms at 1.37M edges with no §7.5 budget**, and
`impact --depth 1 --sites` is 302.0 ms (1.9x the impact row). Both are
pre-existing and unchanged by `d714f29`.

**I5 — `impact --depth 10` on a leaf is 519.4 ms.** Unbudgeted depth, but the
CLI allows it and the depth cap is 10. Depth curve: 10.7 (d3), 519.4 (d10).

### Suggestion

**S1 — The latency gate corpus should contain test symbols.** The current
corpus has zero, so the `tests` row passes on the guard rather than on the
traversal. One test-rich seed would have caught C3.

**S2 — Add `--edges calls,imports` and `--depth 10` cases to the gate**, the
two remaining measured over-budget shapes besides C3.

**S3 — Build cost grew again.** Wall +18.5% to +27% versus `5706dff` (gate
still passes at 0.76-0.81x frozen), peak RSS 245.8 MB (1.34x frozen), index
1.23x. The new counter query is only 29.7 ms of the delta; the rest is
unattributed. An RSS row and a per-stage wall breakdown would make this
reviewable.

**S4 — The hub corpus is not reproducible from committed scripts.**
`tests/scripts/make_synth_corpus.py` generates a 40-function per-file chain
with no cross-file hub, so it cannot regenerate `/tmp/kg-r13-l3/edges1m-sub`.

Background consumers included Microsoft Teams WebView (up to 218% CPU),
`rustc` (154%, including another cycle's build), a `.venv/bin/python` pair
(~36% each), and the ZCode renderer (81%). Load never stayed below 4.6 for
long, and twice exceeded 17.

- Best-of-N (min) is robust to upward noise but cannot recover a sample slowed
  in every run. PASS margins are lower bounds.
- The `tests` numbers are load-insensitive by construction: the guard path is
  sub-10 ms. The reverse-branch numbers were taken at load 6.3-6.7 and agree
  with the load-3.8 anchor of 623.4 ms, so report the band 613-623 ms.
- The impact PASS numbers were taken in one low-load window (4.63). A later
  re-run at load 18 pushed `impact --edges all` to 151.2 ms — over the row —
  which shows the budget margin is load-sensitive at ~19%.
- Cold-cache behavior was not measured. The 306-320 MB indexes stayed in the
  page cache; `purge` needs root. The 3.11 s single build versus 1.76-1.89 s
  best-of-7 shows the effect can exceed 60% on a first run.
- The 3.1M stress numbers are outside the 1M budget and are a scale trend only.
