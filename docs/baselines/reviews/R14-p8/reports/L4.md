## Findings

### Critical (resolved at `d714f29`)

**C1. `impact --depth > 1` silently omitted dependents whose only call edge
source is a module symbol — FIXED.**
At `5706dff`, `src/query.rs:1511-1521` (`impact_source_files`) bounded the
calls-only BFS universe with `SELECT COUNT(DISTINCT file_path) FROM symbols
WHERE kind IN ('function','method')`. Module-level calls emit `calls` edges
whose source is a `module` symbol, so the universe was not an upper bound. The
early break at `src/query.rs:1443-1447` (`if records.len() >= total_files {
break; }`) then stopped the BFS before the module-only dependent was reached.
The same break ran in `--explain` and `--context` modes.

Original reproduction (fresh repo, `kg build`, `--no-journal`):

```
m1.py    def a(): return b()
         def b(): return 1
mid.py   from m1 import a
         def x(): return a()
top.py   from mid import x
         x()

5706dff: kg impact m1.py --depth 2
  m1.py:2
  mid.py:4                      # top.py missing, exit 0, no depth-cap footer
d714f29: kg impact m1.py --depth 2
  m1.py:2
  mid.py:4
  top.py:3
  kg: depth cap 2 reached; deeper dependents may exist
```

Status at `d714f29`: FIXED. `src/build.rs:445-476` stores exact per-kind
source-file counters (`edge_calls_src_files`, `edge_imports_src_files`,
`edge_inherits_src_files`, `edge_all_src_files`) plus
`callable_symbol_count`; `src/query.rs:1514-1558` reads them in O(1) and falls
back to an exact edge scan when the keys are absent (old index) or the kind
set is mixed. Verified on `/tmp/kg-l4-mod2`: depth 2 and 3 include
`top.py:3`; `--limit 1` prints `showing 1 of 3`; `--edges all` includes
`top.py:1`; `--explain` shows `top.py:3 [calls depth=2]`; `--context` includes
the row; MCP `impact depth:2` returns identical text. The old-index fallback
(counters deleted from a copied index) also returns `top.py:3`, and a
fast-path build re-writes the counters. The added regression test is not an
effective guard (I10).

Impact of the original defect: a wrong transitive answer with exit 0 and no
caveat for repositories with top-level callers (`__init__.py` re-exports,
scripts, config modules). `impact --depth 1` and non-calls edge sets were
correct throughout.

### Important

**I1. MCP silently ignores wrong-typed optional arguments.**
`src/mcp.rs:285-298` (`arg_str`, `arg_usize`, `arg_bool`) return the default
when a supplied argument has the wrong JSON type. Only required strings are
validated (`src/mcp.rs:268-283`). Observed on the fixture:

```
tools/call impact  {"file":"m1.py","depth":"2"}       -> isError:false, grouped depth-1 output
tools/call impact  {"file":"m1.py","edges":5}         -> isError:false, edges defaults to calls
tools/call callers {"name":"app.run","limit":"1"}     -> isError:false, 2 rows (limit ignored)
tools/call dead    {"exclude_tests":"true"}           -> isError:false, filter ignored
tools/call api     {"path":"pkg","include_private":"yes"} -> isError:false, flag ignored
```

A client with a schema bug receives a successful wrong answer. This violates
the §4.8 schema intent and the `src/mcp.rs:190-196` comment that invalid
params must be -32602. It affects F1 (`dead`), F4 (`impact`), F6
(`search`/`resolve`), F8 (`tests`), F10 (`api`), and F11
(`exclude_generated`). Fix: type-check every supplied optional argument and
return -32602 on mismatch.

**I2. "Byte-identical to CLI stdout" is false for error results.**
Status: persists at `d714f29`; the README claim is corrected by `5da460a`
("successful tool text matches CLI stdout, and error text appends the CLI
stderr detail"), while `src/mcp.rs:3-4` still says byte-identical.
`README.md:94-96` and `src/mcp.rs:3-4` claim MCP tool results are byte-identical
to CLI stdout. A 39-case parity run (29 success, 10 error) shows success text
is byte-identical, but every error result differs because MCP text appends the
CLI stderr line:

```
CLI:   stdout "kg: clone candidates — ...\n"       stderr "kg: no-results: 0 clone candidates found\n"
MCP:   text   "kg: clone candidates — ...\nkg: no-results: 0 clone candidates found\n"

CLI:   stdout "path:line ...\n"                    stderr "kg: usage: ambiguous name ...\n"
MCP:   text   "path:line ...\nkg: usage: ambiguous name ...\n"
```

`tests/mcp.rs:326-356` pins this channel difference for `unresolved` and
`imports` ("channel differs by contract"). The claim should read "success
result text". Consumers that diff MCP text against CLI stdout fail on every
error result.
